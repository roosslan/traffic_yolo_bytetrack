# traffic_yolo_bytetrack

Подсчёт машин, проезжающих по дороге перед камерой. Машина засчитывается, когда пересекает
виртуальную линию подсчёта. Направление определяется по тому, с какой стороны линии она
приехала. Линий может быть несколько: перед камерой к основной дороге примыкают ещё две,
и линий пять (три участка основной дороги и по линии на каждое примыкание). Каждый проезд
пишется в ClickHouse со снимком; есть сводка по часам.

Что умеет: чтение RTSP-потока с переподключением, днём - поиск машин нейросетью YOLOv8
и сопровождение ByteTrack, ночью - отдельный детектор по фарам, автоматическое переключение
день/ночь, несколько линий подсчёта с направлениями, зона интереса, снимки проездов и запись
в ClickHouse.

## Как устроено

```
кадр > день: YOLO + ByteTrack  \
       ночь: фары + трекер     / > реестр целей > линии подсчёта > снимок, ClickHouse, журнал
```

* **День.** Нейросеть YOLOv8 находит машины (`car`, `motorcycle`, `bus`, `truck`), ByteTrack ведёт
  их под постоянными номерами. Порог уверенности низкий (`conf = 0.1`): машину за
  стеклом нейросеть видит с уверенностью 0.1-0.3, и ByteTrack продлевает по таким детекциям
  уже начатые треки (новые он начинает только от 0.25).
* **Ночь.** Ночью камера видит почти только фары, поэтому нейросеть не нужна:
  фон усредняется, пятна намного ярче фона считаются огнями машин, соседние пятна (две фары)
  склеиваются в одну цель, а цели связываются между кадрами по ближайшему центру с учётом
  скорости. Кадр перед разбором уменьшается до `work_width` (720 px), поэтому основной поток
  2560x1440 разбирается так же быстро, и пороги в пикселях от потока не зависят. ByteTrack тут не подходит: он сопоставляет рамки по перекрытию, а у крошечных
  быстрых точек рамки соседних кадров часто вообще не пересекаются.
* **Выбор режима** (`[daynight] mode = "auto"`). Ночью камера включает ИК-режим и отдаёт серую
  картинку, поэтому серый или тёмный кадр означает ночь. Новый режим включается, только если он
  держится `switch_after_sec` секунд: фары, осветившие кадр, режим не переключат.
* **Проезд.** Цель подтверждена на `confirm_hits` кадрах подряд, последний шаг её пути прошёл
  через отрезок линии, а место, где цель появилась, лежит по другую сторону линии. Направление
  берётся от места появления, а не от прошлого кадра, поэтому дрожание рамки у линии не даёт
  ни двойного счёта, ни смены направления. А то, что пересечение проверяется по реальному
  шагу, а не по прямой от места появления, позволяет засчитывать повороты через короткие линии.
  Через каждую линию цель считается один раз.
* **Перекрёстки.** Основная дорога идёт по диагонали из левого нижнего угла вправо вверх. К ней
  примыкают `side_a` (сверху слева) и `side_b` (снизу; сама дорога в кадр не попадает,
  линия идёт вдоль её устья). Основную дорогу считают три линии: `main_west`
  левее `side_a`, `main_mid` между примыканиями и `main_east` правее `side_b`. Сквозная машина
  пересекает все три, поворачивающая - часть из них и линию своего примыкания.
* **Фары и габариты.** Ночью при боковом ракурсе одна машина даёт два пятна на расстоянии
  своей длины: спереди фары, сзади - габариты (в ИК-режиме красный свет виден ярко). Второе
  пятно пересекает линию через полсекунды после первого. Такой проезд считается повтором, если
  рядом (ближе `merge_distance`) едет только что засчитанная цель в том же направлении.

Три потока: чтение камеры (всегда самый свежий кадр), обработка и запись в
ClickHouse пачками. Если база недоступна, проезды копятся в буфере, а подсчёт продолжается.

## Установка

Нужен Python 3.12 или новее. Быстрый путь на Windows: скрипт ставит пакеты в `venv`, создаёт
`.env` со случайным паролем, поднимает ClickHouse в Docker, создаёт таблицы, делает самопроверку
и прогоняет тесты:

```
powershell -ExecutionPolicy Bypass -File .\setup_dev.ps1
```

Вручную:

```
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

По умолчанию ставится PyTorch для CPU. Дневной детектор (`yolov8s`, `imgsz = 1280`) на CPU
тратит около 220 мс на кадр (4-5 кадров/с), этого хватает, но с видеокартой заметно лучше.
Для видеокарты Nvidia поставьте torch с CUDA (<https://pytorch.org/get-started/locally/>,
например сборку cu126) и в `config.toml` укажите `device = "cuda"`:

```
venv\Scripts\pip install torch torchvision --index-url https://download.pytorch.org/whl/cu126 --force-reinstall
```

Ночному детектору видеокарта не нужна: он тратит около 3-5 мс на кадр.

## Настройка

```
copy config.example.toml config.toml
```

Все параметры описаны комментариями в [config.example.toml](config.example.toml). Неизвестные
ключи и неверные значения отклоняются при старте с понятным сообщением. Координаты на кадре
задаются **в долях кадра** (0..1).

**Поток камеры.** У камеры два потока с разным кадрированием: основной 2560x1440 (отдаётся по
любому пути, кроме `/1` и `/2`, например `rtsp://192.168.1.10:554/0`) и
дополнительный `/1` 720x480, в котором картинка сдвинута по вертикали примерно на 0.1. Линии
в config.example.toml размечены по основному потоку: тогда их можно проверять прямо на
записях основного потока (`--video`). Если перейти на `/1`, линии нужно размечать заново.

| Параметр | Что делает |
|---|---|
| `[[lines]]` | линии подсчёта: `name`, две точки `points`, два названия `directions`; линий сколько угодно |
| `roi.polygon` | зона интереса: цели вне неё не учитываются (парковка, двор) |
| `roi.ignore` | прямоугольники, которые не учитываются никогда: часы и надписи камеры |
| `daynight.mode` | `auto`, `day` (всегда YOLO) или `night` (всегда фары) |
| `headlights.pair_distance` | пятна ближе стольких px - одна цель (две фары одной машины) |
| `headlights.merge_distance` | склейка фар и задних огней одной машины (см. выше) |
| `model.classes` | что считать днём |
| `tracking.confirm_hits` | сколько кадров подряд подтверждают цель |

Линию и пороги удобно подбирать не на живой камере, а на записи:

```
python main.py --video night.mp4             # с окном: видно линию, цели и счётчики
python main.py --video night.mp4 --headless  # быстро, только итог в журнале
```

Время в этом режиме берётся из самого видео, поэтому результат не зависит от скорости
компьютера. ClickHouse при этом не используется, снимки пишутся как обычно.

## Запуск

```
python main.py                    # с окном, выход по клавише q
python main.py --headless         # без окна, остановка по Ctrl+C
python main.py --list             # последние 20 проездов из ClickHouse
python main.py --counts           # проезды по часам за последние 24 часа
python main.py --counts 168       # ...за неделю
python main.py --init-db          # создать базу и таблицы в ClickHouse и выйти
python main.py --self-test        # проверить PyTorch, ultralytics, модель и ночной детектор
```

В окне: красные линии подсчёта с именами, серые игнорируемые области, жёлтый контур зоны
интереса, справа вверху режим и счётчики по линиям. Цели, чей проезд засчитан, рисуются зелёным.

## ClickHouse

`docker-compose.yml` поднимает отдельный сервер на портах **8124** (HTTP) и **9001** (нативный),
чтобы не мешать другому ClickHouse на стандартных портах (8123/9000). Порты открыты на всех сетевых
интерфейсах, поэтому к базе можно подключаться по IP машины (в `config.toml` сейчас
например `host = "192.168.1.20"`) и с других компьютеров сети. Если нужен доступ только с этой машины,
задайте в `.env` `CLICKHOUSE_BIND=127.0.0.1` и выполните `docker compose up -d`. Если к базе
не подключиться с другого компьютера, проверьте брандмауэр Windows (входящие TCP 8124 и 9001).

Пароль берётся из `.env` (`CLICKHOUSE_PASSWORD` для сервера, `TRAFFIC_CLICKHOUSE_PASSWORD` для
программы; setup_dev.ps1 создаёт оба). Таблицы создаются при первом запуске, схема в
[traffic/schema.sql](traffic/schema.sql). Все времена хранятся в UTC, `--list` и `--counts`
показывают местное время.

| Таблица | Что в ней |
|---|---|
| `crossings` | **главная**: одна строка на пересечение линии - линия, направление, время, класс, снимок |
| `events` | захват и потеря каждой цели |
| `tracks` | итог по каждой цели: длительность, число кадров, уверенность, путь |
| `track_points` | траектории, хранятся 30 дней |

Таблицы на движке `ReplacingMergeTree`: повтор оборвавшейся вставки не удваивает данные навсегда,
но до слияния частей дубли видны. Для точного счёта добавляйте `FINAL`:

```sql
-- машины по часам, линиям и направлениям за сегодня (по местному времени)
SELECT toStartOfHour(toTimeZone(ts, 'Europe/Moscow')) AS hour, line, direction, count() AS cars
FROM traffic.crossings FINAL WHERE toDate(toTimeZone(ts, 'Europe/Moscow')) = today()
GROUP BY hour, line, direction ORDER BY hour, line, direction;

-- поток по основной дороге за сутки: одна линия, чтобы сквозные машины не считались дважды
SELECT direction, count() FROM traffic.crossings FINAL
WHERE line = 'main_west' AND ts > now() - INTERVAL 1 DAY GROUP BY direction;

-- сколько было днём (YOLO) и ночью (фары)
SELECT class_name = 'headlights' AS night, count() FROM traffic.crossings FINAL GROUP BY night;
```

## Снимки

В момент проезда в `capture/` пишется снимок с линией, рамками и номерами:
`дд-мм-гггг-чч-мм-сс-класс-линия-idN.jpg`, например
`30-09-2026-21-07-14-headlights-main_west-id2.jpg`. Путь к снимку попадает в `crossings`.
Директория сама не очищается.

## Проверено на камере

**Ночь** (поток `/1`, 720x480):

* 5 минут записи (`data/night_2026-09-30.mp4`): 7 машин, обе линии основной дороги дали
  одинаковый счёт. Без склейки фар и задних огней было бы 12.
* Живой поток: 17-18 кадров/с при 3-5 мс на кадр; запись в ClickHouse по сети
  и чтение через `--list` / `--counts`.

**День** (запись основного потока, 10 минут утром 01.10.2026, солнце в стекло). Эталон -
ручной подсчёт по срезам «место x время» вдоль каждой линии:

| Линия | Эталон | yolov8s, 1280, conf 0.1 | yolov8n, 640, conf 0.1 |
|---|---|---|---|
| main_west | 14 | 14 | 9 |
| side_a | 5 | 5 | 3 |
| main_mid | ~10 | 4 | 6 |
| main_east | ~9 | 0 | 0 |
| side_b | - | 0 | 0 |

Левая часть кадра (чистое стекло) считается точно. Правая часть утром снята сквозь солнечную
засветку на стекле, и нейросеть машин там почти не видит, хотя глазом и на срезах они
хорошо заметны; модели крупнее (`yolov8m`, `yolo11s`) там тоже не помогают. В пасмурную погоду
правая часть дороги видна чисто.

**Не проверено:** ночь на основном потоке и с новыми линиями, переключение день/ночь на
реальном рассвете, дневной счёт `main_mid` и `main_east` в пасмурную погоду, `side_b` на
реальных машинах.

```
tests/           тесты

```

## Ограничения

* Ночью считаются огни, а не машины. Две машины, идущие вплотную (ближе `merge_distance`), будут
  посчитаны как одна. Машина с выключенными фарами не будет посчитана вовсе. Класс машины
  (легковая, грузовик) ночью неизвестен, в базе стоит `headlights`.
* Дуги слева на ночной картинке - отражения фар в стекле. Они доходят
  примерно до x = 0.36 и линии не пересекают. Если линии переносить левее, проверьте это
  на записи (`--video`).
* Пока камера стоит за стеклом, на картинке блики и отражения. Утром солнце засвечивает правую
  половину кадра, и днём `main_mid` и `main_east` сильно недосчитывают. Помогут чистое стекло,
  бленда или козырёк над объективом, объектив, прижатый к стеклу, или камера снаружи. Пока
  этого нет, поток по основной дороге надёжнее всего брать с `main_west`.
* Трекер ведёт цели по положению и движению, а не по внешности. Если цель долго скрыта, трек
  рвётся; проезд, начатый одним треком и законченный другим, может не засчитаться. Поэтому
  линию лучше ставить в середине участка, где машины хорошо видны.
* Ночью в районе перекрёстка свет фар слабеет, и трек
  иногда рвётся: машина засчитывается на обеих линиях, но под разными `track_uid`. Счёт по
  каждой линии от этого не страдает, а вот восстанавливать повороты («приехал с запада, ушёл
  на примыкание») по совпадению `track_uid` на двух линиях пока ненадёжно.
* `ultralytics` по умолчанию отправляет анонимную статистику. Программа отключает её при
  загрузке модели (`sync=False`).
* Не добавляйте в git `config.toml`, `.env`, `models/`, `capture/`, `data/` и `venv/`.
